# 岛屿（Daoyu）项目说明

## 项目是什么

岛屿是一款以 AI 角色沉浸式生活为核心的“小手机”。它不是 AI 助手集合，也不是只有聊天窗口的角色扮演工具。用户创建或导入 Char 后，Char 应拥有稳定的人格、关系、记忆、时间线、日常安排、社交活动和跨应用经历；聊天是主要入口，但不是唯一入口。

岛屿由网页端与 Android APK 共用一套项目源码。网页端提供 PWA/浏览器体验，Android 端通过 Capacitor 接入原生能力。任何开发都必须同时考虑两端，不得擅自改成纯网页产品，也不得擅自替换现有发布链路。

## 当前技术结构

- 页面入口：`index.html`
- 样式：`css-core-*.css`、`css-apps-*.css`
- 核心逻辑：`js-core-*.js`
- APP 逻辑：`js-apps-*.js`
- 主启动与页面注册：`js-main.js`、`js-core-apps.js`
- AI 请求：`js-core-ai.js`
- 提示词引擎：`js-core-prompt-engine.js`
- 记忆引擎：`js-core-memory-engine.js`
- 本地数据：`js-core-storage.js`
- 安卓封装与补丁：`patch_android.mjs`、`patch_keepalive.mjs`、`.github/workflows/`
- 设计规则：`DESIGN.md`
- 数据存储规则：`STORAGE-ARCHITECTURE.md`

项目以经典脚本方式在 `index.html` 中按顺序加载 JS，共享全局作用域。新增或拆分文件时必须检查脚本加载顺序、Service Worker 缓存清单和 Android 打包流程。不要未经评估就引入大型框架或改变模块体系。

## 产品核心原则

1. **角色优先**：输出首先服务于角色扮演和沉浸感，不把 Char 写成助手、客服或万能工具。
2. **人格连续**：角色人设、关系、重要事实和时间线不能因切换 APP 或模型而随意变化。
3. **跨 APP 同一世界**：APP 是同一个世界的不同窗口，不是互不相干的数据孤岛。
4. **事实有来源**：重要事实、事件、承诺和时间必须能追溯来源；未知就保持未知，不允许编造。
5. **用户可控制**：API、模型、场景预设、提示词模块、顺序、上下文条数、记忆策略和衰减天数由用户设置。
6. **模型能力由模型决定**：岛屿不设置自己的固定 Token 上限，不擅自截断必需内容；模型上下文限制、输出限制由实际 API 和模型决定。
7. **完整注入、明确失败**：人设、适用世界书、场景预设、记忆和有效上下文属于必需输入。不得为了“省 Token”静默跳过。若请求超出模型能力，必须明确报错并展示诊断，不得伪装成完整发送。
8. **双端共用**：网页和 APK 共享业务规则与数据结构；原生能力通过明确的适配层接入。
9. **渐进开发**：每次只完成一个明确小任务，先理解现有代码，再修改，再测试，再升版本。
10. **不破坏已有数据**：任何存储结构变化都必须有迁移、备份、回滚和兼容方案。

## 开发与验证

当前 `package.json` 提供：
- `npm run build`：执行现有静态资源构建脚本。
- `npm run stamp`：更新版本戳。
- `node test-prompt-engine.mjs`
- `node test-memory-engine.mjs`
- `node test-chat-facts-integration.mjs`

涉及提示词、记忆、API 请求或跨 APP 数据时，必须运行相关测试。涉及 UI 时至少检查日间、夜间、网页窄屏和 Android WebView。发布前检查网页和 APK 的版本号、缓存更新、原生权限和数据兼容。

## 版本与发布

每次用户确认的功能更新默认递增版本。遵循仓库现有 `stamp-version.mjs`、`changelog.json`、Service Worker 和 GitHub Actions 流程。不要擅自新增一个独立网页部署产物目录，也不要改动生产分支或发布配置，除非用户明确要求。
